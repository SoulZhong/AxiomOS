# 把你的 Agent 接入 AxiomOS

AxiomOS 对 Agent 只有一个接口：MCP（Streamable HTTP）。任何支持 MCP 的 Agent（Claude Code、Codex、自研脚本）挂上就能领任务、干活、回传结果。系统永远不主动连进你的机器，Agent 只做出站连接。

## 1. 注册 Agent，拿到令牌

在网页「Agent」页面点「注册 Agent」，填名称、运行时、能力标签、授权，提交后系统显示**一次性令牌**（`axm_` 开头）。令牌只显示一次，丢了就吊销重新注册。

授权决定 Agent 能做什么，且不会超过你本人的权限：

| 授权 | 让 Agent 可以 |
|---|---|
| 执行任务 | 领取分配给你的任务、开始执行、上报用量、提交结果 |
| 领取任务 | 从待领取任务里自己领 |
| 验收 | 作为验收人通过或打回 |
| 评论 | 发评论、写工作日志 |
| 创建子任务 / 创建任务 / 创建目标 | 对应动作 |
| 指派 / 建立关联 | 对应动作 |
| 管理流程 | 修改任务类型与流程；对 Agent 只能是"需要人确认" |

每项授权都可以设成「直接生效」或「需要人确认」。设成「需要人确认」时，你调用对应工具不会立刻改动系统，而是生成一条**待确认操作**，等人点确认后系统再以你的身份执行一次（见下面第 8 节）。

## 2. 挂到 Claude Code

```
claude mcp add --transport http axiomos http://localhost:8080/mcp \
  --header "Authorization: Bearer axm_你的令牌"
```

然后在 Claude Code 里说"看看我在 AxiomOS 上有什么任务"即可。

## 3. 挂到其他 MCP 客户端

MCP 端点：`POST /mcp`，请求头：

```
Authorization: Bearer axm_你的令牌
Content-Type: application/json
Accept: application/json, text/event-stream
```

## 4. Agent 的工作循环

系统在 MCP 的 instructions 里已经写了这套流程，Agent 会自动遵循：

1. `list_my_tasks` 看分配给我的任务；`list_backlog` 看可领取的。
2. `get_task_brief` 读任务说明（描述、目标链、评论、前置任务的结果、执行指令）。
3. `get_workflow` 看现在能走哪一步、不能走的原因。
4. 进入进行中阶段后 `begin_task` 开启执行记录；每 60 秒 `heartbeat` 并上报**累计**用量。
5. `attach_artifact` 附上要求的交付物，`transition_task` 推进（如 `submit`、`dev_done`）。
6. 需求不清用 `transition_task` 的 `ask_for_input` 提问并等待；过程记录用 `add_note`。

所有拒绝理由都是中文句子，Agent 应据此行动而不是重试。

## 5. 用量与成本

`heartbeat` 的 `usage` 按模型分条，填**累计值**（幂等，系统取最大）：

```json
{"task_id": "tsk_xxx", "usage": [
  {"model_id": "claude-sonnet-5", "input_tokens": 120000, "output_tokens": 18000, "cache_read_tokens": 40000, "tool_calls": 55}
]}
```

系统按价格表折算成组织结算货币，实时计入任务、目标、执行者的成本。执行记录结束时以最后一次上报为准；心跳超过 10 分钟没来，执行记录会被判为超时结束，任务回到负责人手上。

## 6. 心跳超时与并发

- 执行中每 60 秒心跳；10 分钟没心跳判超时。
- 注册时的「并发上限」限制同时进行的执行记录数，超过则领取与开始都会被拒绝。

## 7. 看板与迭代

Agent 和人看到的是同一份数据（ADR 0012）：看板是任务按流程状态分列的视图，迭代是一段时间内承诺完成的一批任务。

| 工具 | 作用 |
|---|---|
| `list_sprints` | 列出迭代（可按团队、状态过滤），含任务数、工作量合计、已完成工作量 |
| `get_sprint` | 一个迭代的详情：迭代目标、起止日期、迭代待办、燃尽图、迭代速度 |
| `add_tasks_to_sprint` | 把任务加入迭代待办；已结束的迭代会拒绝 |
| `remove_task_from_sprint` | 把任务移出迭代待办 |
| `get_board` | 看板：每张卡片的 `can_move_to` / `moves` 由内核按你的身份与授权算出，拖动就是调用 `transition_task` 走对应的步骤；列上的 `over_limit` 表示超出在制品上限，只提醒不拦截 |
| `start_sprint` / `close_sprint` | 需要「管理流程」权限。对 Agent 这类操作必须经人确认，调用后会生成一条待确认操作，等人确认才真正开始或结束 |

任务的 `points`（工作量）在 `create_task` 后可由所有者在网页上填写；燃尽图与迭代速度按它计算，没填时按任务数。

## 8. 里程碑

里程碑是目标在时间轴上的刻度：到某一天应该达到什么（ADR 0016）。它**不是任务**——没有负责人、没有流程、没有执行记录，不会出现在待领取任务或看板里；它只回答"目标是否按节拍推进"。「已达到」由人确认，系统不自动判定。

| 工具 | 作用 |
|---|---|
| `list_milestones` | 一个目标自己的里程碑（不含子目标）：名称、日期、`status`（`upcoming` 未到 / `reached` 已达到 / `overdue` 已逾期）、`ready_hint`（该日期前计划结束的任务都已完成，可以确认了） |
| `create_milestone` | 在目标上新增里程碑：`goal_id`、`title`、`due_on`（YYYY-MM-DD）、可选 `description` |
| `reach_milestone` | 确认里程碑已达到。只在它对应的事真的做到了之后调用 |

里程碑受「创建目标」授权约束（它是目标的一部分）：没有这项授权会被拒绝；授权模式是「需要人确认」时，调用会生成一条待确认操作（见下一节），等人确认后才生效。每次改动都会留下动态。

## 9. 待确认操作（需要人确认的授权）

某项授权是「需要人确认」时，命中它的调用会返回这样一句话，而不是报错：

```
已提交待确认操作，等小李确认后才会执行。待确认操作 ID：prp_xxx。用 list_my_proposals 看它的状态，不要重复提交同一个操作。
```

这时系统什么都没改：任务状态、评论、交付物、关联、迭代都保持原样。人在网页上点「确认」后，系统会以**你的身份**把这一步重新执行一次，动态照常记在你名下，并注明「经<确认人>确认」；点「拒绝」则会给出一句完整的中文理由，你按理由行动，不要重试。

| 工具 | 作用 |
|---|---|
| `list_my_proposals` | 列出你提交的待确认操作，可按 `status`（pending / approved / rejected / expired）过滤 |

会走这条路的动作（取决于你的授权设成了哪种模式）：推进流程、领取任务、开始执行、指派、评论与工作日志、附交付物、建立关联、创建任务 / 子任务 / 目标、新增 / 修改 / 删除里程碑与确认里程碑已达到、修改任务类型与流程、开始 / 结束迭代。

待确认操作七天没人处理会自动过期，需要重新提交。
