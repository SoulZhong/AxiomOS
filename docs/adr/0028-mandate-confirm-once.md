# ADR 0028：委托——确认一次，做到底；问人的单位是决定，不是操作

日期：2026-09-09 · 状态：已采纳（2026-09-09 落地第 1–7 步，网页在第 8 步） · 关联：0002（动态是唯一事实来源）、0003（权限交集与待确认操作）、0006（执行记录只由本人开启）、0014（什么可配）、0020（外部事件）、0025（确定性交互）、0026（目标方案）、0027（客户端里确认）、`docs/design/collaboration-from-first-principles.md`

## 背景

一天的真实使用（`docs/design/sources/collab-retro-brief-2026-09-08.md`）：一个目标拆成 9 个任务全部交给一个 Agent，实际工作几小时做完，把状态推到终态却要所有者点头约 30 次，每次只看到一句话。所有者的原话：确认太多、信息不够、要在网页和 Agent 之间来回切、看不到进展与成本。Codex 的评审（`collab-retro-codex-2026-09-08.md`）补了另一面：Agent 在没有执行记录时先把活干完，再用一串待确认操作把既成事实补录进流程；「经确认」不知道确认的是哪个版本。

根因是 ADR 0003 把授权建在**操作类型**上：「附交付物」「推进」「开始执行」各是一项，每项可以要求人确认，于是人把一件事交出去之后，还得为这件事的每个动作点头。人信任的对象从来是「这件事交给它」，不是「它可以附交付物」。

## 决策

### 1. 委托是授权的单位

**委托**（code: `Mandate`）是所有者把**一个任务**交给一个 Agent 的凭据。一份委托只覆盖一个任务；目标方案批准时给方案里每个任务各发一份，共用一个 `plan_id`，`(task_id, agent_id)` 上同一时刻最多一份活动中的委托。字段：

| 字段 | 含义 |
|---|---|
| `task_id` / `agent_id` / `owner_id` | 哪个任务、交给谁、谁交的（发出委托的人；方案批准时是目标负责人） |
| `plan_id` | 来自哪份方案，直接指派时为空 |
| `budget_cost` / `budget_tokens` / `deadline` | 预算。本 ADR **只存不算**：记账口径、原子扣减、超预算处理全部在 ADR 0030 定义，那之前预算只是给人看的意向 |
| `side_effects` | 对外动作逐项许可。本 ADR 只有一项 `external_link`（对应现有 `task.external_link` / `task.external_link_remove`）；`push_code`、`send_message` 保留名字，等有对应的 Agent 写路径时再启用，启用前一律视为未许可 |
| `ask_me` | 这份委托里仍要问人的事（第 1.3 条） |
| `grants_snapshot` | 发出时 Agent 的授权副本；委托内的判定与重放都用它，不用当前授权 |
| `task_version` / `assignee_id` | 发出时的任务版本与负责人 |
| `status` | `active` / `revoked` / `stale`（失效） |

#### 1.1 怎么产生（三条路，都由人触发）

- **批准目标方案**：一次批准 = 方案里每个任务一份委托（第 4 条）。
- **人把任务指派给 Agent**：按组织默认的委托模板自动发一份；指派页上能改。
- **Agent 领取待领取任务**：组织可配「领取即委托」或「领取后问一次」（默认后者，问的那份决定就是发委托）。

所有者随时可收回（`revoked`）。收回后 Agent 在这个任务上的后续写动作回到 ADR 0003 的逐项判定，正在进行的执行记录不动。

#### 1.2 有效权限

**有效权限 = 所有者权限 ∩ Agent 的授权（发出时的快照）∩ 委托范围 ∩ 流程当前步骤。** 前两项是 ADR 0003 的原样；委托范围只加不减：一个动作在委托之内、且属于下面这张**白名单**，就直接生效，不看该项授权是「直接生效」还是「需要人确认」：

| 动作 | 现有授权 | 条件 |
|---|---|---|
| 附交付物、写进展、提交结果 | 执行任务 | 任务是委托的那个任务 |
| 心跳与用量 | （遥测） | 同上 |
| 按流程推进 | 执行任务 | 步骤的 `by` 含 `assignee`，步骤没有声明 `grant` 或声明的是「执行任务」，去向不是失败终态。验收步骤（`grant: review`）、流程管理、取消一律不在名单内 |
| 提问等待 | 执行任务 | 同「按流程推进」 |
| 评论 | 评论 | 任务是委托的那个任务 |
| 建子任务 | 创建子任务 | 上级是委托的那个任务 |
| 建立关联（相关 / 发现于 / 前置） | 建立关联 | 一端是委托的那个任务；解除前置仍按 ADR 0003 一律问人 |
| 挂 / 摘外部链接 | 执行任务 | `side_effects.external_link` 打开 |

不在名单里的动作（改负责人、取消、删除、验收、改目标、方案外新建、改流程、解除前置）仍按 ADR 0003 走。

**判定只有一处。** 内核 `Executor` 多一个字段 `Mandate *MandateScope{TaskID, Grants, SideEffects}`；`domain.NeedsApproval(actor, grant)` 之外新增 `domain.NeedsApprovalFor(actor, task, action)`，白名单写在内核里，应用层不许自己判「在不在委托内」。应用层只有一个装载点 `App.executorFor(ctx, sess, taskID)`：读活动中的委托、校验它没失效、装进 `Executor`。现有直接调 `NeedsApproval` 的写路径（`tasks.go`、`review.go`、`codeplatform.go`、`observe.go`、`sprints.go`、`goals.go` 等）逐一改成经 `executorFor` + `NeedsApprovalFor`，清单进实施计划；改完之前不打开委托的判定（功能开关），避免半套。

#### 1.3 `ask_me` 与硬约束的优先级

三层，高的压低的：

1. **硬约束（写死，谁都关不掉）**：验收别人的任务、改流程、删除、目标的结论（达成 / 放弃）、解除前置、里程碑删除与撤销。这些对 Agent 永远逐条问人（ADR 0003 补记的「一律待确认」原样保留）。
2. **组织默认**：`reassign`（改负责人）、`cancel`、`create_outside_plan`（方案外新建）、`accept`（任务级人工验收）。组织在委托模板里勾，所有者只能**加**勾不能去勾。
3. **所有者微调**：在组织默认之上多勾几项。

`ask_me` 只作用于白名单之外的动作：勾了就问，没勾的按 ADR 0003 那项授权的模式。

#### 1.4 失效

以下任一发生，委托变 `stale`，记 `MandateStale` 动态并通知 Agent 与所有者：任务换负责人、任务换目标、任务类型换版本、Agent 被吊销或所有者停用、`grants_snapshot` 里用到的授权被所有者收回、任务到终态。`stale` 之后不自动续发；人再指派或 Agent 再领取时按 1.1 重新发。

### 2. 执行记录随第一个写动作自动开启

委托之内，下面这些动作里的第一个在任务的「进行中」阶段发生时，自动开一段执行记录：附交付物、写进展、提交结果、按流程推进、提问等待、挂外部链接。评论、建子任务、建关联、心跳是**准备动作**，不开执行记录。开启与那次写动作在**同一个事务**里：写失败就没有执行记录，也没有空壳。

ADR 0006 的精神不变：仍是 Agent 自己的动作开启，不是状态进入时自动开；变的只是不再要人为「开始」这件事点头。`begin_task` 工具标记为弃用：仍可调，效果等同一次心跳；指令与文档不再提它。心跳超时后的「中断待续」在 ADR 0030 落地。

每条委托内的写动作记账三件事：委托编号、执行记录编号、对象版本（进动态的 `data`）。

### 3. 撤回：只撤推进，只追加不删除

委托内直接生效的**推进**，所有者在 24 小时内可撤回一次：任务回到上一状态，记 `TaskReverted` 动态（带被撤的那条动态编号、原因）；旧动态不删（ADR 0002）。可撤的边界用任务版本判：只允许撤最近一步推进，且那步之后任务版本没有再变（任何写入都会加版本，包括评论）。撤回在同一个事务里校验版本。交付物与进展说明本期不做撤回：那是追加的事实，要撤也只能追加「已撤回」标记，留到有需要时再议。对外副作用不可撤，所以默认全关。

### 4. 目标方案带验收方式与参与角色，批准即委托

`propose_goal_plan` 的每个任务多两项（预算继承规则留到 ADR 0030）：

- `acceptance`：`auto`（默认）或 `human`。
- `participants`：任务类型有参与角色时，方案里逐槽写明执行者（成员或 Agent 的 ID）。默认由提案的 Agent 把所有槽填成自己；这是显式写在方案里、人看得见能改的，人批准即是对「兼任」的授权。校验：成员要有该槽的角色；Agent 要么就是这个任务的负责人（兼任，靠批准授权），要么其所有者有该槽的角色。任务类型级的「负责人可兼任哪些角色」配置不在本期。

方案预览（网页与 `/confirm` 两边同一份）每个任务标明：负责人、参与角色、验收方式、**首步能不能走**（`by` 规则、角色、能力的预检）。**走不了的任务不能批准**：预览里标红并给原因，人改了负责人或参与角色才能批；勾掉它也行。

批准时把这些一起落库并给每个任务发委托（`plan_id` 相同）。方案落库仍是 ADR 0026 的一个事务；委托在同一个事务里。

### 5. 自动验收：系统执行者，人选的

`acceptance = auto` 的任务在流程走到「待验收」时，系统检查验收步骤自己声明的要求（现有 `requires` 能表达的：`artifact:*`、`no_open_bugs`、`deps_done`）；都满足就走验收步骤。为此内核多一种执行者 `ExecutorSystem` 与一个专用入口 `domain.AutoAccept(c)`：它不参与 `by` 判定、不看授权、不开执行记录、只能走 `grant: review` 且去向是成功终态的那一步（同 ADR 0020 外部事件的定位）。动态记 `TaskAutoAccepted`（按方案的验收标准），验收人一栏仍是人，打回照旧由人做。要求不满足就停在「待验收」，等 Agent 补齐后再试（每次相关写动作后重试）。

自动验收是人在方案里**逐任务选**的，不是默认给所有任务的；组织可以在委托模板里把默认改成 `human`。交付物的真实性（PR 是不是真的 PR）在 ADR 0031 加强，加强后自动验收的条件随之收紧，本 ADR 不假装已经解决。

### 6. 方案验收：一份决定认整个方案

方案里最后一个任务到终态时，系统生成**一份**动作为 `plan.review` 的待确认操作，确认人是目标负责人。它是一个**捆**（第 7 条）：每个 `human` 验收的任务一项（同现有的验收步骤，逐项通过 / 打回，打回带原因给 Agent），外加方案关联的里程碑各一项（勾上即「已达到」）。每项都有交付物（带验证状态）、执行记录与成本。全是 `auto` 的方案也生成这份，只是没有要勾的任务，只有里程碑和一份总览。目标的达成仍是人的单独动作，不并进来。

一个目标只在两处需要人：批准方案、方案验收。

### 7. 决定：捆、版本、快照

待确认操作从「一条操作」变成「一个人能一口气回答的问题」：

- **捆**（`bundle_id`）：Agent 在同一任务上提出新的待确认操作时，若该任务上已有它自己提的、仍在等待的一条，就并入同一捆；没有时间窗口，以「前一条还没被答」为准。一捆一次答，逐项可剔除；剔除的记为拒绝（理由是「所有者在这一捆里剔除了它」），其余按提出顺序重放，一条失败不影响已成功的（各自事务，各自动态）。
- **版本**：任务与目标各加一个单调递增的 `version` 列，每次写入加一（在 store 层统一做）。待确认操作记 `target_version`；答的时候在同一个事务里 `SELECT … FOR UPDATE` 锁住那条、比版本：不一致即置 `stale`、通知 Agent、不重放。同一条被两个人同时答只会成功一次。
- **快照**：待确认操作记提出时的 `grants_snapshot`；重放用快照，不用当前授权（现有 `withDirectGrants` 把当前授权全部变成直接生效的做法废止）。
- `stale` 的待确认操作留作记录，不能再答；要不要重提由 Agent 决定（它收到通知与理由）。

展示带足信息：改前改后对比、交付物可点开、执行记录与成本。术语沿用「待确认操作」，改名为「决定」放在 ADR 0029 与客户端一起换。

### 8. 不做的事

- 不给 Agent 任何替人做决定的工具；`decide_proposal` 的凭证规则（ADR 0027）不变。
- 不做「按 Agent 全局放行」：委托永远绑定一个任务，换人即失效。
- 不为减少确认让 Agent 跳过流程阶段。
- 不改人（成员）的权限模型；委托只关 Agent。
- 不改 `by: creator` 的判定、不做重连续接、不做同一所有者的 Agent 共享配额：那是 ADR 0031 的事，本 ADR 不宣称解决了责任链断裂。
- 不做每日摘要与预算执行：ADR 0030。

## 被否决的

- **保留逐项授权，只把「需要人确认」合并成批次**：少点几次，但人确认的仍是操作而非结果，「确认的是哪个版本」照旧。
- **验收全部交给人、只是合成一份**：写得出客观标准的验收本来就该系统做。
- **让委托覆盖一个目标下所有任务（一份）**：撤回、预算、任务转移、审计归属都要按任务分；一份多任务的委托只是把这些拆分推迟到实现里。
- **自动验收伪装成验收人本人**：问责链造假；系统执行者是唯一合法路径。
- **撤回时删除动态或交付物**：违反 ADR 0002。

## 后果

- 新表 `mandates`；`tasks`、`goals` 加 `version`；`tasks` 加 `acceptance_mode`、`plan_id`；`proposals` 加 `bundle_id`、`target_version`、`grants_snapshot`；`runs` 加 `mandate_id`。
- `internal/domain`：`ExecutorSystem`、`Executor.Mandate`、`NeedsApprovalFor`（白名单）、`AutoAccept`、`Revert`。
- `internal/app`：`executorFor` 单一装载点；委托的发放 / 收回 / 失效；方案批准落委托与验收方式；方案完成生成 `plan.review`；待确认操作的捆、版本、快照、`FOR UPDATE` 决定；写路径迁移清单与功能开关。
- 网页：指派页与确认页改为委托模板；方案预览加参与角色、验收方式、可达性并阻止不可达的批准；「待我处理」按捆显示；任务页多「撤回」。
- MCP：`propose_goal_plan` 多 `acceptance` / `participants`；`get_workflow` 与 `get_task_brief` 返回委托状态（在不在委托内、要问人的事）；`begin_task` 弃用。
- 新动态：`MandateIssued` / `MandateRevoked` / `MandateStale` / `TaskAutoAccepted` / `TaskReverted` / `PlanReviewRequested` / `PlanReviewed` / `ProposalStale`。
- 新词（CONTEXT.md）：委托、委托模板、自动验收、方案验收、撤回。
- 以本次目标为例，人出手的次数从约 30 次降到 2 次。

## Codex 评审（2026-09-09）的处理

第一版被指出的 P1 逐条处理：判定统一到内核一处并列迁移清单（1.2）；委托固定为每任务一份（1）；重放用授权快照（7）；对象版本与 `FOR UPDATE`（7）；撤回改为追加事实、只撤推进（3）；预算本期只存不算（1）；自动验收改为系统执行者专用入口（5）；推进白名单排除验收、流程管理、取消（1.2）；副作用只保留有对应写路径的 `external_link`（1）；身份与续接明确不在本 ADR（8）。砍掉：每日摘要（→0030）、`begin_task` 的可选语义（弃用）、交付物与进展说明的撤回、共享并发配额。保留但收窄：自动验收（人逐任务选、只用现有 `requires`）、方案验收（做成捆而不是新状态机）。
