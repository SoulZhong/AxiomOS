# Agent 的权限 = 所有者权限 ∩ 授权，且授权可以要求人确认

系统对 Agent 开放几乎全部操作（领任务、验收、建目标、甚至修改流程），这带来"Agent 越权"和"Agent 失控"两类风险。我们决定：每个 Agent 必须有一个人类所有者（公共 Agent 的所有者是组织负责人），Agent 的有效权限是所有者自身权限与所有者显式给出的授权（`Grant`）的交集；每项授权可以设为"直接生效"或"需要人确认"，后者会生成一条待确认操作（`Proposal`），人点确认后才执行。修改流程这类改规则的授权，对 Agent 只允许"需要人确认"。

## Considered Options

- **Agent 完全继承所有者权限**：接入最省事，但一个被提示注入的 Agent 就等于所有者本人。
- **Agent 拥有独立于人的角色体系**：灵活，但打断了问责链，"这个 Agent 为什么能做这件事"无人可答。
- **交集 + 可选人类确认（选定）**：所有者权限收缩时 Agent 自动收缩；高风险动作用待确认操作保住 Human in the Loop，而不是一刀切禁止 Agent。

## Consequences

- 不存在无主 Agent；成员停用时其全部 Agent 即刻吊销。
- 成本与问责按所有者归集；公共 Agent 的成本归组织负责人。
- 待确认操作是一等实体，有自己的动态与生命周期；同一机制可套用于任何授权，由各组织自行决定哪些动作需要人把关。

## 实现补记（2026-09-04）

- 待确认操作已实现：内核区分授权模式，Agent 命中「需要人确认」的动作时返回专门的信号，应用层据此记下一条待确认操作而不执行；人确认后按记录重放，拒绝必须写完整句子的理由，七天未处理自动过期。被覆盖的动作见 `docs/api.md`「待确认操作」。
- 修任务字段（`PATCH /tasks/{id}`）此前没有任何授权检查，任何持有令牌的 Agent 都能改任何任务，违反本决策。现在规则是：Agent 只能修改自己负责或自己创建的任务，且需要「执行任务」授权（模式为需要人确认时走待确认操作）；验收人、优先级、归属目标、迭代、参与角色、「仅限人工」属于人的决定，Agent 一律不能改。
- 仍未受授权约束的写路径：心跳与用量上报（遥测，不改变用户可见状态）。

## 补记（2026-09-06，ADR 0020）

**外部事件不是第三种执行者的权限口子。** 代码平台的回调走的是同一个内核（`domain.ApplyExternal` → 与 `Apply` 同一段迁移实现），不能绕过状态机：

- 它没有授权，也不参与 `by` 判定——组织唯一的开关是"这一步写不写 `triggered_by`"。写了就等于组织明确同意"这件外部事件可以走这一步"，与"给 Agent 一项授权"是同一性质的显式授予。
- 它永远不为谁开始执行记录，因此不会替某个人"顶班"产生成本记录。
- 外部操作者绑定成员时（`external_identities`，`kind = git_user`），动态显示成那个人，但那只是署名：他的角色与权限不参与这次迁移的判定。

**Agent 挂外部链接**与发评论同一套规则：要有「执行任务」授权，授权是「需要人确认」时先记一条待确认操作（动作 `task.external_link`），人确认后由系统以 Agent 名义执行。链接只能挂在 Agent 看得见的任务上（可见范围照 ADR 0013 判）。

## 补记（2026-09-08，Agent 能力补齐第一批）

MCP 给 Agent 补齐了目标的读与改、任务编辑、外部链接、里程碑完整生命周期与验收（清单见 `docs/plans/2026-09-agent-capabilities.md`）。新工具沿用本决策，另定三条边界：

- **目标的问责链与结论一律待确认。** `update_goal` 改标题、说明、日期、时间粒度、时间桶、信心度、成果指标、类型按「创建目标」授权的模式走；改**负责人、上级、团队**，以及**达成 / 撤销达成 / 放弃 / 重新开始**（`achieve_goal` 等四个工具），不看授权模式，Agent 一律先记一条待确认操作（动作名 `goal.update / goal.achieve / goal.unachieve / goal.abandon / goal.restart`）。批量改时间桶与重排（`goal.horizon / goal.rank`）整批记成一条，人一次确认一整批。目标的删除不给 Agent。
- **不可逆与推翻人的结论的动作一律待确认。** 删除里程碑、撤销里程碑的「已达到」（`milestone.delete / milestone.unreach`）对 Agent 不看授权模式。摘外部链接与挂外部链接同一套规则（`task.external_link_remove`）。
- **验收是一等能力。** `review_task(decision, comment, checked_deliverables)` 按步骤自己的声明（需要「验收」授权、去向状态的类型）挑出验收通过 / 打回那一步，走的是与人完全相同的内核路径；`get_workflow` 给出 `is_reviewer` 与两步的名字。目标的进展说明（`add_goal_note`）与任务上的工作日志同一套规则：要「评论」授权。

「一律待确认」在重放一条已确认的待确认操作时不再拦（会话带着确认人），否则确认会绕成圈。

## 补记（2026-09-08，第二批：观测）

- 看动态、看统计、看组织上下文都是只读，不需确认；成本按财务范围（ADR 0013），自己上报的用量永远给自己看。
- 迭代的创建与修改按「创建任务」授权走（迭代是任务的时间盒）；开始与结束仍按「管理流程」且 Agent 必经人确认（ADR 0012）。
- 解除关联与建立关联同一项「建立关联」授权；解除**前置**关系会改变依赖图，Agent 一律先经人确认（`task.unlink`）。
- Agent 没有自己的收件箱：`list_my_notifications` 给它的是所有者通知里挂在它有份的任务上的那些，`mark_notifications_read` 也只能标这些。所有者本人的事不给 Agent。

## 补记（2026-09-08，第三批：目标方案）

「领取目标」落为一条动作为 `goal.plan` 的待确认操作（ADR 0026）。它是本决策的两个例外：不看授权模式（整份方案一律经人审）；确认人是**目标负责人**而不只是 Agent 的所有者（载荷里的 `decider_id`，`canDecideProposal` 认它）。批准时按方案一次落库，任务直接就绪——就绪那一步要的「执行任务」授权由这次批准补上（只在落库的那个事务里）。

## 补记（2026-09-09，ADR 0028：委托）

授权仍是能力上限，但「需要人确认」这一档在**委托**之内不再起作用：人把一个任务交给 Agent（批准目标方案、指派、批准领取）即发一份委托，有效权限变成 所有者权限 ∩ 授权（发出时的快照）∩ 委托范围 ∩ 流程当前步骤。委托内的白名单动作（附交付物、写进展、`by` 含负责人且只要「执行任务」授权的推进、提问、评论、子任务、关联、许可打开时的外部链接）直接生效并自动开执行记录；白名单之外的动作，以及本决策各补记里「一律待确认」的那些（验收别人的任务、改流程、删除、目标结论、解除前置、里程碑删除与撤销）不变。判定只在内核 `domain.NeedsApprovalFor` 一处。待确认操作从此记提出时的授权快照，重放只用快照（`withDirectGrants` 只剩内核校验探针的用途）；对象被别人改过即失效，不再重放。
