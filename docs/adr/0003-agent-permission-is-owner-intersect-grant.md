# Agent 的权限 = 所有者权限 ∩ 授权，且授权可以要求人确认

系统对 Agent 开放几乎全部操作（领任务、验收、建目标、甚至修改流程），这带来"Agent 越权"和"Agent 失控"两类风险。我们决定：每个 Agent 必须有一个人类所有者（公共 Agent 的所有者是组织负责人），Agent 的有效权限是所有者自身权限与所有者显式给出的授权（`Grant`）的交集；每项授权可以设为"直接生效"或"需要人确认"，后者会生成一条待确认操作（`Proposal`），人点确认后才执行。修改流程这类改规则的授权，对 Agent 只允许"需要人确认"。

## Considered Options

- **Agent 完全继承所有者权限**：接入最省事，但一个被提示注入的 Agent 就等于所有者本人。
- **Agent 拥有独立于人的角色体系**：灵活，但打断了问责链，"这个 Agent 为什么能做这件事"无人可答。
- **交集 + 可选人类确认（选定）**：所有者权限收缩时 Agent 自动收缩；高风险动作用待确认操作保住 Human in the Loop，而不是一刀切禁止 Agent。

## Consequences

- 不存在无主 Agent；成员停用时其全部 Agent 即刻吊销。
- 成本与问责按所有者归集；公共 Agent 的成本归组织负责人。
- 待确认操作是一等实体，有自己的动态与生命周期；同一机制可套用于任何授权，由各组织自行决定哪些动作需要人把关。

## 实现补记（2026-09-04）

- 待确认操作已实现：内核区分授权模式，Agent 命中「需要人确认」的动作时返回专门的信号，应用层据此记下一条待确认操作而不执行；人确认后按记录重放，拒绝必须写完整句子的理由，七天未处理自动过期。被覆盖的动作见 `docs/api.md`「待确认操作」。
- 修任务字段（`PATCH /tasks/{id}`）此前没有任何授权检查，任何持有令牌的 Agent 都能改任何任务，违反本决策。现在规则是：Agent 只能修改自己负责或自己创建的任务，且需要「执行任务」授权（模式为需要人确认时走待确认操作）；验收人、优先级、归属目标、迭代、参与角色、「仅限人工」属于人的决定，Agent 一律不能改。
- 仍未受授权约束的写路径：心跳与用量上报（遥测，不改变用户可见状态）。

## 补记（2026-09-06，ADR 0020）

**外部事件不是第三种执行者的权限口子。** 代码平台的回调走的是同一个内核（`domain.ApplyExternal` → 与 `Apply` 同一段迁移实现），不能绕过状态机：

- 它没有授权，也不参与 `by` 判定——组织唯一的开关是"这一步写不写 `triggered_by`"。写了就等于组织明确同意"这件外部事件可以走这一步"，与"给 Agent 一项授权"是同一性质的显式授予。
- 它永远不为谁开始执行记录，因此不会替某个人"顶班"产生成本记录。
- 外部操作者绑定成员时（`external_identities`，`kind = git_user`），动态显示成那个人，但那只是署名：他的角色与权限不参与这次迁移的判定。

**Agent 挂外部链接**与发评论同一套规则：要有「执行任务」授权，授权是「需要人确认」时先记一条待确认操作（动作 `task.external_link`），人确认后由系统以 Agent 名义执行。链接只能挂在 Agent 看得见的任务上（可见范围照 ADR 0013 判）。
