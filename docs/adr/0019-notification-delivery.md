# ADR 0019：通知外发分三层

日期：2026-09-06　状态：已接受

## 背景

「待我处理」只在站内。Agent 提交待确认操作、任务等验收、任务逾期时，人往往不在系统里，需要在飞书、企业微信或邮件里收到并一键打开。调研 Kaneo 后确认其分层做法可取（`docs/design/sources/kaneo.md` §2）。

## 决定

1. **三层**：
   - **系统事实**：「待我处理」与站内通知不变，是唯一事实源；外发只对新产生的事项生效，不回放历史，失败不阻塞业务写入。
   - **组织允许范围**：组织负责人在「组织设置 → 通知」里决定允许哪些通道（飞书、企业微信、邮件、webhook）与哪些事件类型可以外发（待确认操作、等我验收、指派给我、提问、逾期、里程碑到期）。默认只允许飞书 / 企业微信（已接入 IM 时）与邮件。
   - **个人偏好**：每人在「我的偏好 → 通知」里为每种事件选通道与安静时段；只能在组织允许的范围内选。默认：待确认操作与等我验收走 IM 私聊，其余只站内。
2. **通道是提供方的一种能力**：飞书、企业微信的"发消息"能力挂在 IM 集成的提供方注册表上（`internal/directory` 的 Provider 增加可选的 `Messenger` 接口），复用同一套凭据与接入检查（新增检查项「能以应用身份发消息」）。邮件（SMTP）与 webhook 是独立的简单提供方。
3. **投递记录**：每次外发记一条投递（事件、通道、状态、错误原话、时间），个人和组织都能在通知设置里看最近投递；连续失败达到阈值时在检查清单里亮黄。
4. **消息内容**：一句话正文（与站内句子相同）+ 一个直达链接（`PUBLIC_URL` 拼接）；不含成本与他人信息。
5. **不做**：不做实时聊天、不做会话式交互、不在 IM 里执行确认（第一版只跳转）。

## 后果

- 新表：通知通道配置（组织级）、个人通知偏好、投递记录。
- 投递由调度器异步执行，带重试与去重（同一事项同一通道只发一次）。
- 与 ADR 0014 一致：允许范围可配，"站内是事实源、外发不阻塞"写死。

## 补记一：出网与重放（2026-09-06，安全审查）

- **出网默认只许公网**。webhook 通道的接收地址由组织管理员填，托管场景下不能让它把服务器指到内网或云元数据接口。判断规则写死在 `internal/directory/egress.go`：只认 http(s)（没打开内网出网时只许 https）、不许带用户名密码、不许指向回环 / 私网 / 链路本地 / 唯一本地 / 组播 / 未指定地址；云元数据地址任何时候都不许。保存时按域名查一遍，连接前按解析出的地址再查一遍（`net.Dialer.Control`，DNS 改绑绕不过去），重定向也过同一道。私有化部署把接收端放在内网是正当需求，由部署方设置环境变量 `AXIOMOS_ALLOW_PRIVATE_EGRESS=1` 显式打开——与 ADR 0014 一致：允许什么由部署方决定，判断规则本身不可配。出网代理地址同一套规则。
- **签名带新鲜度窗口**。`X-AxiomOS-Signature` 的 `t` 用发出这一刻的时间（不是消息生成时间，重试过的消息也要落在窗口里）；接收方先看 `t` 与当前时间相差是否在 5 分钟内，超出就丢弃，再做常数时间比较。截获的旧请求不能任意重放。
