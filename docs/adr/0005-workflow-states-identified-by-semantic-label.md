# 系统依据状态类型而非状态名识别流程状态

流程允许组织自定义并版本化，状态名可以是任意文本（"开发中"、"fixing"、"待上线"）。系统内核需要知道"哪个状态算完成"（进度、周期统计）、"哪个状态是在干活"（执行记录）、"哪个状态在等人"（通知）。我们决定每个状态必须归入且仅归入一种状态类型（`StateLabel`）：未开始（`pending`，可标记为可领取）、进行中（`active`）、等待中（`waiting`）、已完成（`terminal_success`）、已终止（`terminal_failure`）。内核只读状态类型，永不匹配状态名。

## Considered Options

- **约定固定状态名**（所有流程必须含 todo、in_progress、done）：简单，但自定义流程被迫复用不贴切的名字，且 Bug 流程的"不是 Bug / 重复 / 不修复"这类多个终止态无法表达。
- **内核直接解释状态名 + 特例列表**：随每个自定义流程膨胀，最终内核与配置耦合。
- **状态类型（选定）**：状态名归业务，类型归内核；执行记录、进度、通知、甘特图都只依赖五种类型。

## Consequences

- 流程校验规则：初始状态必须存在、至少一个"已完成"状态、每一步的起点终点必须存在。
- 执行记录与"进行中"状态的关系见 ADR 0006：离开进行中状态结束执行记录，但进入进行中状态不自动开始执行记录。
- 进行中的任务钉在创建时的流程版本上，状态类型的含义在版本间保持稳定，是内核唯一允许依赖的契约。
