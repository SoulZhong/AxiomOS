# ADR 0027：在 Agent 客户端里确认待确认操作

日期：2026-09-08 · 状态：已采纳 · 关联：0003（待确认操作）、0025（斜杠命令）、0026（目标方案）

## 背景

「需要人确认」的授权让 Agent 的每一步都变成一条待确认操作，人得离开 Agent 客户端、到网页的「待我处理」里点确认，再回到客户端告诉 Agent「确认了」。一个任务从开始到提交要来回三四次，人说这交互太别扭。但 ADR 0003 的底线不能破：**Agent 不能替人确认**，否则「需要人确认」就是摆设。

## 决策

1. **确认走斜杠命令 `/confirm`，凭证只能由人触发。** 斜杠命令是 MCP 提示（ADR 0025）：客户端在人敲命令的那一刻向服务器取提示（`prompts/get`），Agent 自己调不到这一步。服务器趁这一步发一张**确认凭证**（nonce）写进提示文本，Agent 再拿凭证调 `decide_proposal` 转达。凭证证明的只有一件事：人刚刚敲了这条命令。
2. **凭证的范围就是人点名的范围。** `/confirm` 不带参数只列清单，不发凭证；`which=all` 覆盖此刻等这个人确认的全部，`which=<ID>` 只覆盖那一条；`decision=reject` 的凭证不能用来确认，反之亦然；拒绝必须带 `reason`。每条只能用一次，十分钟过期。Agent 拿凭证做不了人没说的事。
3. **裁决以所有者本人的身份记账。** `decide_proposal` 在服务端换成所有者的会话去执行原有的确认 / 拒绝逻辑（同一段代码、同一套权限判定），动态记在人的名下，末尾注明「（在 Agent 里确认，由 X 转达）」。
4. **目标方案在这里只能整份批准。** 逐条勾选仍在网页上做（ADR 0026）；提示里写明这一点。
5. **凭证放在进程内存里。** 十分钟的生命周期、只对发它的那条连接有意义，不值得一张表；多实例部署时再挪进表。后台巡检顺手清过期的。

## 被否决的

- **给 Agent 一个 `approve` 工具，靠提示词约束它只在人同意后调**：提示词只能提高概率，挡不住越权；这正是 ADR 0003 要防的。
- **MCP elicitation（服务器向客户端弹表单）**：机制上最干净，但依赖客户端支持，且我们的 MCP 是无状态的 Streamable HTTP，服务器发不出反向请求。等客户端普遍支持后可以补成第二条路。
- **确认一次放行整条任务**：能减少次数，但那是改「需要人确认」的粒度，另议。

## 后果

- 斜杠命令从八条变成九条；新增工具 `decide_proposal`；`Session` 多 `ViaAgentID / ViaAgentName`；动态 `ProposalApproved / ProposalRejected` 的数据里多 `via_agent`。
- 「待我处理」里每条待确认操作直接列出要确认的内容（`ProposalDetails`），网页与客户端两边看到的是同一份。
