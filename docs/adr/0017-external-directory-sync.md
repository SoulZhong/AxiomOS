# ADR 0017：外部目录同步——飞书是组织结构的来源，人员只停用不删除

日期：2026-09-06 · 状态：已采纳 · 关联：ADR 0001、0013、0014

## 背景

客户的组织结构与人员名单已经维护在飞书这类办公套件里，不应在本系统里再手工维护一份。本系统是可定制的 SaaS 并支持私有化部署（ADR 0014），集成必须按组织配置、凭据不落明文、私有化环境可能经代理出网。

## 决策

1. **外部目录是结构与名单的来源**：同步把飞书的部门树对齐成团队树（部门 ↔ 团队，一一映射，父子关系跟随），把人员对齐成成员。本系统里手工建的团队与成员仍然允许，但被同步覆盖范围内的对象以外部目录为准；冲突时外部目录赢，并记入动态。
2. **只停用不删除**：外部目录里消失的人 → 成员停用（其 Agent 吊销、任务回待领取，沿用现有停用逻辑）；消失的部门 → 团队标记为「已停用」而不删除，历史归口不变。
3. **同步进来的人是「待激活」成员**：有名字、团队、角色（默认一个组织配置的角色），能被指派任务，但要通过邀请链接设密码后才能登录；飞书单点登录作为后续能力单独决策。
4. **外部身份存独立表**：`external_identities(org_id, provider, kind: member|team, external_id, local_id)`，同一对象可以有多个提供方的身份，为将来接企微、钉钉留位置。
5. **按组织配置**：应用凭据（App ID / App Secret）、同步根部门、默认角色、同步频率（手动 / 每小时 / 每天）都在组织设置里；App Secret 用服务端密钥加密后入库，界面只显示是否已配置。私有化部署可配置出网代理。
6. **每次同步是一次可追溯的运行**：记录开始结束时间、新增 / 更新 / 停用数量、错误列表，产生动态 `DirectorySyncRan`；失败不回滚已成功的部分，下一次同步是幂等的。

## 代价

- 引入对外部服务的依赖与凭据管理；需要密钥加密与代理配置。
- 同步覆盖范围内的团队与成员在本系统里不可改名（会被覆盖），界面上要标出「来自飞书」。

## 被否决的方案

- **本系统为准、反向写飞书**：客户的行政流程在飞书里，反写会造成两边打架。
- **同步时直接创建可登录账号并发初始密码**：没有邮件通道，且不安全；邀请链接是现成机制。
- **物理删除离开的人与部门**：违反本系统"记录不删"的一贯原则，成本归口会失真。

## 补记（2026-09-06）：提供方抽象，先接企业微信

用户要求同时支持企业微信，并且"适配不同的软件，抽象设计屏蔽平台差异，符合开闭原则"。决定：

- **提供方是插件**。`internal/directory` 里每个平台一个文件，实现同一个 `Directory` 接口（取令牌、读部门树、读部门人员、可选读企业名），并在包初始化时 `Register(Provider{...})` 到注册表。应用层、存储层、接口层、前端都不再出现任何平台名的分支：新增一个平台 = 新增一个文件 + 一条词汇表说明，其余代码不改。
- **凭据按提供方声明**。每个提供方声明自己的凭据字段（键、标题、是否保密、占位、提示）与接入前置条件；配置表把凭据存成一个 JSON 对象（保密字段加密），不再有 `app_id/app_secret` 这类飞书专属列。前端表单按声明渲染。飞书：App ID、App Secret；企业微信：企业 ID（CorpID）、通讯录同步 Secret。
- **统一的外部模型**。部门 `{id, name, parent_id, deleted}`、人员 `{id, name, email, mobile, dept_ids, active}`；`RootDepartmentID` 由提供方给（飞书 "0"，企业微信 "1"）。平台差异（分页方式、字段名、令牌有效期、错误码体系）全部封在客户端里，向上只暴露 `RejectedError` / `UnreachableError` 两类错误和原话。
- **一个组织一个提供方**。切换提供方等于换来源：旧外部身份保留但不再匹配（成员照常存在），同步预览会把它们列成"来自旧来源、将改为手工维护"，不自动停用。
- 企业微信接口（自建应用 + 通讯录同步 Secret）：`gettoken`、`department/list`、`user/list?fetch_child=1`；人员编号用 `userid`；`status` 1 已激活、2 已禁用、4 未激活、5 退出企业。企业微信对新建应用的敏感字段（姓名、手机、邮箱）有权限限制，没有权限时只同步能拿到的字段并在同步结果里说明。

## 补记二（2026-09-06）：接入是一条被引导的路

用户在真实飞书企业上试了一遍，卡在三处：根部门被权限范围拒绝（40004）、部门和人员读得到但没有名称（字段级权限缺失，接口却返回成功）、不知道该去哪里开什么权限。结论：**接入不能靠用户查资料**，系统要自己诊断并告诉人下一步做什么。

- **提供方声明检查项**（`Diagnose`）：每个提供方实现一组有序检查，每项返回 `{key, title, status: ok|todo|blocked|skipped, detail, fix, fix_url}`。检查项由提供方自己定义（飞书：凭据可用、通讯录权限范围、部门名称权限、人员姓名权限、邮箱权限、版本已发布；企业微信：凭据可用、可信 IP、敏感字段权限）。`fix` 是一句"去哪儿点什么"，`fix_url` 尽量是**这个应用**在控制台里的那一页（飞书 `https://open.feishu.cn/app/{app_id}/auth` 等）。
- **应用层只编排，不认识平台**：`GET /org/directory/checklist` 依次跑检查并汇总为向导状态：当前在第几步、哪一步卡住、下一步该做什么。
- **前端是一个向导**：选平台 → 填凭据（保存即测试）→ 按检查项逐条修（每条有「打开」链接和「我已处理，重新检查」）→ 选同步范围（整个企业或从被授权的部门里选）→ 预览 → 同步 → 定时。全部通过前不显示「立即同步」。已接入后同一页显示检查项的即时状态，坏了能看见。
- 字段被权限裁掉的情况（读得到部门没有名字）视为**阻塞**，不允许把无名团队同步进来。

## 补记三（2026-09-06）：更名

用户要求把「外部目录」更名为「IM 集成」（界面、词汇表、文档一致；接口路径 `/org/directory/...` 与代码内部名不变）。飞书、企业微信都是即时通讯平台，这个名字也为后续接消息通知、免密登录留了位置。

## 补记四（2026-09-06）：冲突在预览里解决，对应关系随时可改

系统里已经手工建了人和团队，之后再从 IM 或 CSV 导入时会撞车：没邮箱认不出人、同名团队重复、花名覆盖手工姓名、手工分配的团队被静默替换。决定：

- **认人认团队分五级**：外部身份（以前绑过的）→ 邮箱 → 手机号 → 姓名且上级团队同名 → 同名且两边唯一（IM 里和系统里都只有这一个叫这个名字的人）；团队为外部身份 → 同名且同层级（父团队也对上）。第一级直接算同一个；其余各级只产生**候选**，进预览的「需要你确认」区，不自动合并。
- **三种决定**：合并到已有、作为新建、跳过。决定存成记录（提供方、外部编号、决定、本地对象），下次预览不再问；「跳过」的对象在预览里列为已跳过，可随时改主意。有未决定的候选时，同步按钮说「还有 N 条要先确认」，不执行。
- **合并后的字段归属**：姓名、团队归属、在职状态由 IM 决定；角色、Agent、任务、目标、成本口径由本系统管，同步永不碰。来源标为「来自{IM}」。
- **团队合并**：旧团队的成员、目标、任务、迭代、共享边界整体并入目标团队，旧团队停用不删除，产生一条动态。
- **对应关系可查可改**：「IM 集成」页新增「对应关系」面板：已绑定（IM 对象 ↔ 本地对象，可解绑）、可能重复（同步后系统仍会用同一套认法在手工对象和同步对象之间找疑似重复，可在这里合并）、已跳过。成员页对疑似重复的人显示「可能与 X 重复」提示，点开就是合并。
- **手动预览随时可用**：接入完成后「预览同步」保留在状态视图里，任何时候都能重新跑一遍，看到将要发生的改动和当前的候选冲突，再决定是否同步。
- CSV 导入走同一套认法和确认区。
