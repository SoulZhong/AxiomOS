# 调研：Kaneo（Codex 独立视角，2026-09-06）

> 由 OpenAI Codex CLI（codex-cli 0.153.4）在只读模式下独立调研 Kaneo 源码与文档并对照 AxiomOS 的 CONTEXT.md / ADR / DESIGN.md 后生成，原文未改。与 `kaneo.md`（Claude 视角）并读，对照见后者末尾。


## 一、调研前提：两个产品解决的问题不同

Kaneo 是一个围绕“工作区—项目—任务”的轻量项目管理工具。它的核心价值是让团队快速建立任务、分派、推进、复盘的共同视图；AxiomOS 则是“目标→任务→人和 Agent”的组织操作系统，除了执行，还要处理流程、成本、可见范围、组织结构与外部目录同步。

AxiomOS 的设计基线已经很清楚：管理策略可配置，但系统正确性、权限、成本口径必须固定（`docs/adr/0014-configurable-saas.md`）；目标和任务必须在界面上明确区分（`web/DESIGN.md`「目标与任务的区分」）；Agent 是一等执行者，而不是附加的自动化插件。

## 二、Kaneo 做得好的地方

### 1. 信息架构围绕“同一批任务的不同看法”

Kaneo 把项目下的任务拆成 Board、List、Backlog、Calendar、Gantt 等视图，而不是为每种视图创造不同对象。文档明确说，Backlog 是“planning layer”，其中 `planned` 状态只是数据状态；看板中的 “Backlog” 列也只是普通列（`apps/docs/core/functional/backlog-planning.mdx`）。

这带来两个体验好处：

- 用户可以按会议场景切换视图，不需要重新理解数据。
- 状态、筛选、排序、任务详情在不同视图间保持一致。

界面上也有相同的约束：`apps/web/src/routes/.../project/$projectId/` 下分别提供 `board.tsx`、`backlog.tsx`、`calendar.tsx`、`gantt.tsx`，任务详情仍由同一套组件承载。

这与 AxiomOS 的 ADR 0012、0015 高度一致：看板、甘特图、迭代、待领取都应该是任务之上的视图或容器，而不是平行数据模型。

### 2. 任务详情把“执行信息”和“协作上下文”放在一个连续空间

Kaneo 的任务详情同时包含标题、说明、外部链接、子任务、关系、评论和活动时间线（`apps/web/src/components/task/task-details-content.tsx`）。文案中还有明确的 “Open in full page”，说明它先支持快速抽屉查看，必要时再进入完整页面（`i18n/en-US.json` 中 `tasks.detail.openInFullPage`）。

这是一种很成熟的渐进式信息密度：

- 看板卡片负责快速扫描；
- 抽屉负责快速处理；
- 全页负责复杂编辑与完整上下文；
- 活动时间线负责回答“发生过什么”。

AxiomOS 可以直接借鉴到任务详情和目标详情：执行者首先看到任务说明、目标链、前置任务结果、交付物和当前待办；需要深入时再展开完整历史。尤其适合 Agent 执行场景，避免把所有流程、授权、成本信息一开始全部铺开。

### 3. 任务卡片为高频扫描做了大量细节优化

`apps/web/src/components/kanban-board/task-card.tsx` 显示，卡片可以根据用户偏好控制任务编号、负责人、优先级、截止日期、标签和子任务计数；支持拖拽、键盘操作、批量选择、右键菜单，并对 Pull Request 显示 open、draft、merged 状态。

文案也保持简单直接，例如：

- `Unassigned`
- `Due this week`
- `Move to Backlog`
- `Archive all completed tasks`
- `No scheduled tasks`

这些词不会要求用户学习复杂术语。AxiomOS 的中文词汇表原则可以延续这种克制，尤其是 Agent 状态、待领取、执行记录等新概念，优先使用可理解的日常表达。

### 4. 筛选、排序和视图切换被做成持续可用的工具

`apps/web/src/components/board/board-toolbar.tsx` 把状态、优先级、负责人、截止日期、标签筛选、排序和 Board/List 切换放在同一个工具栏，并以可移除的 active filter chip 展示当前条件。这样用户可以看到“自己正在看什么”，也能快速撤销某个条件。

AxiomOS 的 `web/DESIGN.md` 已提出“一条筛选栏管全部任务页签”，这是正确方向。Kaneo 提供的具体借鉴是：筛选条件应该持久可见、可单独移除，并且随着 List、Board、Gantt 切换保留，而不是每个页面重新设置。

### 5. 工作区级标签形成了统一语言

Kaneo 的标签在工作区级定义，改名或改颜色会影响所有使用该标签的任务（`apps/docs/core/functional/manage-workspace-labels.mdx`）。文档还明确说明，管理标签需要 `Manage settings` 权限。

这同时解决了三个问题：

- 团队可以形成共同分类语言；
- 用户不用在每个项目重复配置；
- 权限边界清楚，普通成员不会随意改变组织语义。

AxiomOS 可以把这套思路扩展为“能力标签”和任务类型：由组织负责人维护词表，Agent、任务和流程都引用同一套标签，避免每个团队各自定义“会做什么”。

### 6. 通知系统区分“站内消息”和“外部投递”

Kaneo 已经有站内 notification inbox，账户通知设置则在其上增加 Email、ntfy、Gotify、Webhook 等外部渠道；而且渠道设置是个人的，工作区规则另行决定哪些工作区可以发送（`apps/docs/core/functional/account-notifications.mdx`）。

这个设计将“系统记录了什么”和“用户希望如何接收”分开，避免通知偏好污染业务数据。AxiomOS 的“待我处理”可以借鉴这种分层：

- 待我处理是系统事实；
- 通知是提醒方式；
- 飞书、企业微信、邮件是外部投递；
- 处理完成后，历史仍保留。

### 7. MCP 不是演示功能，而是完整的任务操作面

`packages/mcp/README.md` 列出了工作区、项目、任务、评论、标签、关系、时间记录等工具；`packages/mcp/src/tools/register.ts` 为每个工具定义了明确的 Zod 输入约束，并要求先通过 `list_project_columns` 获取合法状态。

值得借鉴的产品设计不是工具数量，而是“Agent 需要先获取上下文，再执行动作”的交互契约。AxiomOS 可以将其进一步提升为：

- 先获取当前范围、任务说明和可用流程；
- 再领取或开始执行；
- 需要人工确认的操作进入“待我处理”；
- 每个动作给出可理解的失败原因。

## 三、值得落到 AxiomOS 的部分

### 1. 把视图统一到“任务”入口

AxiomOS 已在 `web/DESIGN.md` 中规划“任务”下的列表、看板、甘特图、迭代、待领取页签。建议沿用 Kaneo 的原则：这些页面只改变观察角度，不改变任务身份。

例如：

- 看板回答“任务现在处于哪一步”；
- 甘特图回答“什么时候发生”；
- 迭代回答“这一段时间承诺做什么”；
- 待领取回答“我能接什么”。

这能避免目标、任务、迭代、执行记录之间形成重复的状态体系。

### 2. 将任务详情设计成“执行简报”

Kaneo 的任务详情适合做基础框架，但 AxiomOS 需要加入自己的关键内容：目标链、参与角色、前置关系、任务类型指令、授权状态、执行记录、成本和验收入口。它们应按照“现在要做什么→为什么做→前面发生了什么→如何验收”的顺序组织，而不是按照数据库字段排列。

这尤其有利于 Agent：Agent 不需要浏览多个页面拼装上下文，任务说明本身就是可执行的工作包。

### 3. 借鉴工作区级配置，但保持策略边界

Kaneo 的工作区级标签、角色、工作流和通知规则说明：组织级设置可以统一团队语言。AxiomOS 应将这一做法用于流程、任务类型、能力标签、价格表和工作台预设。

但根据 ADR 0014，不能把所有规则都开放配置。可见范围、Agent 有效权限、成本归口、状态语义仍必须由系统保证，不能变成客户可任意修改的“偏好”。

### 4. 将 MCP 工具对应到可见的用户动作

Kaneo MCP 的工具命名清晰，适合作为 AxiomOS 的基础。AxiomOS 应进一步让每个 MCP 动作在界面上有对应物：Agent 创建任务后能看到动态，Agent 需要确认时进入待我处理，Agent 执行产生的成本出现在组织概况和成本页。

这样 Agent 和人使用同一套业务语言，而不是另有一套隐藏 API 语义。

## 四、不适合直接照搬的部分

### 1. Kaneo 的 Project 中心模型不足以承载组织目标

Kaneo 的核心层级是 Workspace→Project→Task。AxiomOS 需要 Goal→Task，并允许目标嵌套、里程碑、目标负责人和汇总进度。若直接把 AxiomOS 做成“项目列表”，会让目标变成任务容器，无法表达组织意图与结果责任。

### 2. Kaneo 的成员模型不能直接表达 Agent

Kaneo 的任务负责人主要是用户，MCP 只是让外部程序操作用户可操作的资源。AxiomOS 中 Agent 有所有者、在线状态、最多同时任务数、授权、待确认操作和成本归口，这些是执行者的一等属性，不能仅作为头像或自动化集成附属在用户旁边。

### 3. Kaneo 的权限结构偏项目管理，不足以表达范围与财务隔离

Kaneo 文案中的角色权限包括 Project、Task、Label、Workspace 的 Create、Read、Update、Delete、Assign 等（`i18n/en-US.json`）。这适合控制“能不能操作”，但 AxiomOS 还需要区分“能看到哪个范围”和“能看到哪些成本”。ADR 0013 的共享边界、组织级可见性策略和跨边界例外不能用普通项目权限替代。

### 4. 轻量状态列不适合替代 AxiomOS 流程

Kaneo 的工作流配置重点是项目列、状态和自动化规则（`configure-workflows.mdx`）。AxiomOS 的流程还涉及参与角色、状态类型、迁移条件、负责人交接、执行记录和 Agent 授权。可以学习 Kaneo 的易配置体验，但不能把流程简化成“拖到某一列”。

### 5. 外部通知渠道不等于组织协同集成

Kaneo 的 Email、ntfy、Gotify、Webhook 主要是把通知发出去。AxiomOS 的飞书、企业微信集成还要同步组织结构、团队、成员、待激活状态、冲突候选和停用逻辑（`docs/adr/0017-external-directory-sync.md`）。这不是通知偏好，而是组织事实来源，产品流程应完全不同。

## 五、容易被忽略的细节

1. **Backlog 不是状态名的同义词。** Kaneo 文档特意说明，Backlog 视图中的 `planned` 与看板里的 “Backlog” 列不是同一个概念。AxiomOS 也要避免把“待领取”“迭代待办”“未开始状态”混成一个列表。

2. **空状态文案在引导下一步。** Kaneo 使用 “Add a start date, due date, or both...” 这类文案解释为什么日历为空，而不是只显示“No tasks”。AxiomOS 的目标空状态可以直接引导“先拆几个任务出来”，这与 `web/DESIGN.md` 的状态摘要句一致。

3. **删除、归档、移动的后果被明确写出来。** 例如标签删除会从所有任务移除且不可撤销，项目删除会永久删除数据。AxiomOS 处理目标放弃、成员停用、团队合并、Agent 吊销时，也应在动作附近说明影响范围。

4. **“可见配置”与“可执行动作”要分开。** Kaneo 的个人通知设置、工作区投递规则已经体现这一点。AxiomOS 的工作台布局、默认范围、通知渠道可以个人调整，但权限、成本口径和 Agent 授权不能被个人偏好覆盖。

5. **任务历史不是附属日志。** Kaneo 的 `comment`、`notification`、`activity`、`taskRelation` 都有独立数据结构，任务详情统一呈现。AxiomOS 的 ADR 0002 将动态定义为系统骨架，这意味着每次状态变化、领取、交接、确认和成本产生都应成为用户可理解的历史，而不只是后台审计记录。

6. **MCP 的错误应成为用户体验的一部分。** Kaneo MCP 通过状态列查询和错误结果返回避免盲写。AxiomOS 应把越权、范围不可见、待确认、前置未完成、Agent 达到并发上限等错误写成完整中文理由，并在界面与 MCP 中保持同一套解释。
