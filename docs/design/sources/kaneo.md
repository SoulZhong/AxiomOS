# 调研：Kaneo（usekaneo/kaneo，2026-09-06 快照）

开源自托管项目管理工具，MIT。口号"less is more"：工作区 → 项目 → 任务，看板 / 列表 / 待办 / 日历 / 甘特五种视图，标签、优先级、截止日、子任务与阻塞关系、评论、时间记录。技术栈 Hono + Better Auth + Drizzle/PostgreSQL，React + TanStack Router/Query，Turborepo 单仓。约 1.2k 个 TS 文件。

## 和 AxiomOS 的定位差异

Kaneo 是"给人用的轻量任务板"：没有目标层、没有 Agent、没有成本、没有流程状态机、没有组织层级与可见范围。我们是"目标 → 任务 → 人和 Agent"的组织操作系统。所以借鉴的不是它的领域模型，而是它在**接入体验、通知路由、自动化、可移植性、工程纪律**上的做法。

## 值得借鉴

### 1. Agent / MCP 接入体验（最值得）
- 每个实例自带 `/api/mcp` Streamable HTTP 端点，**OAuth 2.1 + PKCE**：客户端第一次连上会跳到网页登录并明确批准，之后所有工具以该用户身份运行。另有 stdio 包走**设备授权码**（打印一个验证码和网址，浏览器里批准）。
- `npx @kaneo/mcp` 交互式安装器：选 Cursor（用户级 / 项目级）、Claude Desktop、自定义 JSON，自动写配置。
- 同时兼容 MCP 2026-07-28 无状态协议与 2025 会话式协议，并把兼容契约、测试、回滚写成文档。
- 我们现在是"注册 Agent → 复制令牌 → 手工贴进配置"。可以借鉴：① 设备码授权，让 Agent 端一条命令完成绑定，不复制令牌；② 安装器一键写入各客户端配置；③ 与「接入向导」一样把 Agent 接入做成向导（ADR 0017 补记二的原则）。注意我们的 Agent 是独立执行者、有自己的授权范围（ADR 0003），不是"以用户身份运行"，设备码授权应绑定到 Agent 身份而非替代它。

### 2. 通知路由分三层
- 账号级通道（邮件、ntfy、Gotify、自定义 webhook）配置一次；工作区级规则决定哪个工作区允许用哪个通道；项目级再收窄（全部 / 选定项目）。站内收件箱永远是事实源，外发只对新通知生效、失败不阻塞。
- 我们「待我处理」只有站内。可以借鉴这套分层，把"通知到飞书 / 企业微信 / 邮件"做成个人偏好 + 组织允许范围，而且提供方复用 IM 集成的插件注册表。

### 3. 自动化规则与外部链接
- `workflow_rule`：项目里把「集成事件」映射到「目标列」（如 GitHub PR 合并 → 移到 Done）。`external_link` 把任务和 PR / Issue / 外部资源关联，`activity` 记录外部来源的操作者（externalUserName/Avatar/Source）。
- 我们的流程是状态机 + 角色流转，可以在流程定义里加"外部事件触发迁移"（Git 平台的 PR 合并、CI 通过），并把外部执行者记进执行记录；这与 Agent 回传结果是同一条路。

### 4. 键盘与命令面板
- 前缀式快捷键：`p c` 新建项目、`t c` 新建任务、`v b/l/k/c` 切视图、`n o` 打开通知、`j/k` 上下、`?` 帮助；命令面板列出"建议、项目、成员、命令、主题"。
- 我们有 ⌘K 与部分快捷键；可以补齐"视图切换、新建、上下移动"的前缀式快捷键并在 `?` 里列出。

### 5. 任务模型的小细节
- 任务有**项目内序号**（`number`）：可读的 `#123`，比我们的 `tsk_xxx` 友好，可加"组织内序号"作为显示编号。
- 待办（backlog）是任务的一种状态，不是一个列；这与我们 ADR 0012"看板是视图"一致，可作佐证。
- 关系类型只有三种：subtask / blocks / related，够用。我们的 found_in（Bug 阻塞需求发布）是它没有的，保留。
- 每个用户可配置"任务显示哪些字段"（序号、负责人、截止日、标签、优先级）、默认视图、紧凑模式——对应我们工作台区块的 compact，可以扩展到任务列表列的个人偏好。

### 6. 公开只读项目
- 项目可开"公开访问"，生成只读链接，无需登录。我们可以给目标 / 迭代做"只读分享链接"，给外部干系人看进度与甘特图。

### 7. 数据可移植
- 任务 CSV/JSON 导入导出、从 Planka 迁移的独立包、Helm chart、Coolify 编排、一键部署 CLI（drim）。私有化部署的 SaaS 尤其需要：导入导出（我们已有成员 CSV，可扩展到任务 / 目标）、从 Jira / 飞书项目 / Notion 导入、Helm。

### 8. 工程纪律（可直接抄）
- `AGENTS.md` 是给 AI 代理的"操作指南"，写清边界（API 是授权唯一权威、隐藏按钮不算权限）与"改一个行为要追到哪些面"（路由 / 校验 / 权限 / 事件 / WebSocket / 缓存 / MCP / 文档 / 迁移 / 反向状态）。我们的 CLAUDE.md 可以增加"变更追查清单"。
- i18n：`en-US.json` 是唯一事实源，脚本检查所有语言缺键、多键与复数类别；OpenAPI 文档是提交的产物并有一致性检查。我们中英词典靠人工对齐，值得加一个缺键检查脚本。
- 动效改进以"计划"形式落在 `plans/` 里（motion tokens、transition 收敛、命令面板即时、按压反馈、reduced-motion、看板重排），每条标注严重度与依赖顺序，做完标 DONE，并列出"审核过不用修的项"。
- 权限词表独立成包：资源 × 动作的声明，内置角色由词表组合，自定义角色存库。我们 ADR 0013 的权限已接近，可把词表抽成一处声明并让"角色 → 权限"页面按声明渲染，与提供方声明同一思路。

## 不打算借鉴

- 工作区 / 项目两层容器：我们以目标树与团队树承担这个职责，不另加"项目"。
- 以"列"为状态：我们坚持状态类型与流程定义（ADR 0005、0012）。
- 计费 / 试用 / 座位数逻辑：私有化部署优先，不进内核。
- 多个社交登录提供方：企业场景先做 IM 免密登录（飞书 / 企业微信），后续再看。

## 建议的落地顺序

1. Agent 接入向导 + 设备码授权 + 安装器（复用 IM 接入向导的形态）。
2. 通知外发的三层路由，提供方走 IM 集成插件。
3. 任务显示序号、任务列表列偏好、前缀式快捷键补齐。
4. 流程定义支持外部事件触发迁移；Git 平台集成作为第一个事件源。
5. i18n 缺键检查脚本与 CLAUDE.md 变更追查清单。
6. 目标 / 迭代只读分享链接；任务与目标的导入导出。

## 与 Codex 调研的对照（见 `kaneo-codex.md`）

**两边一致**：视图是同一批任务的不同看法（佐证 ADR 0012）；通知分"系统事实 / 提醒方式 / 外部投递"三层；MCP 是完整操作面且"先取上下文再动作"；Kaneo 的项目容器、以列为状态、项目级权限不适合我们。

**Codex 单独提出、值得采纳**：
- 任务详情按"现在要做什么 → 为什么做 → 前面发生了什么 → 如何验收"组织成执行简报，而不是按字段排列；抽屉 → 全页的渐进密度。
- 筛选条件以可单独移除的芯片持久显示，并在列表 / 看板 / 甘特切换时保留。
- 组织级词表（标签、任务类型、能力标签）由负责人维护，Agent、任务、流程引用同一套。
- 删除、归档、停用、合并这类动作要在动作旁写清后果（我们 IM 集成里已这样做，应推广到目标放弃、Agent 吊销等）。
- 空状态文案要引导下一步。
- MCP 的错误要写成完整中文理由，界面与 MCP 用同一套解释。

**本篇单独提出**：设备码授权 + 安装器；外部事件触发流程迁移；前缀式快捷键；任务可读序号；个人显示偏好；公开只读链接；导入导出与迁移；工程纪律（AGENTS.md 变更追查、i18n 缺键检查、权限词表、动效计划）。
